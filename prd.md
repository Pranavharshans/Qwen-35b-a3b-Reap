# Product Requirements Document: Reverse-REAP v0

## 1. Document control

| Field | Value |
|---|---|
| Project | Reverse-REAP: coding-expert localization and extraction |
| Version | v0.1 |
| Status | Approved scope for prototype execution |
| Primary donor | `Qwen/Qwen3.5-35B-A3B` |
| Domain | Software engineering and code generation |
| Primary output | Causally validated layer-expert shortlist plus extracted expert tensors |
| Explicitly deferred | Training or merging the experts into a smaller host model |
| Future gate | Repeat the validated procedure on GLM-5.3-Flash only after v0 succeeds |

## 2. Problem statement

REAP normally uses a calibration corpus to estimate each routed expert's contribution and remove experts with low saliency. This project uses the same router-weighted activation evidence in the opposite operational direction: rank and retain experts that may be disproportionately important for a chosen domain.

The prototype must determine whether Qwen3.5-35B-A3B contains reproducibly identifiable layer-expert pairs that are specifically important for coding. It must then extract the corresponding tensors without claiming that the tensors form a standalone coding model.

Routing frequency is not capability attribution. A coding prompt can activate experts responsible for English, formatting, reasoning, or common tokens. Reverse-REAP therefore treats routing and REAP saliency as candidate-generation signals and requires causal ablation before calling any candidate "coding-critical."

## 3. Goals

### G-001 — Reproducible telemetry

Capture token-level router selections, router weights, and expert-output activation norms from the pinned donor checkpoint with enough metadata to reproduce every observation.

### G-002 — Domain-specific ranking

Rank layer-expert pairs by differential importance on coding tasks versus matched non-coding controls, rather than by raw activation frequency alone.

### G-003 — Causal validation

Demonstrate that masking a selected expert set damages coding performance more than matched random expert sets and does not cause an equally large general-performance collapse.

### G-004 — Lossless extraction

Copy the validated experts' tensors and required quantization metadata into a versioned artifact, then prove byte-for-byte equality with the source tensors.

### G-005 — Autonomous, auditable execution

Make each experimental stage resumable, budget-bounded, deterministic where possible, and governed by machine-checkable gates suitable for an unattended coding agent.

## 4. Non-goals

The following are outside v0:

- Training a bridge or adapter into any smaller model.
- Merging, averaging, distilling, pruning, or deleting donor experts.
- Claiming that extracted tensors work independently of the donor model.
- Cybersecurity-specialist discovery.
- GLM-5.3-Flash execution.
- Fine-tuning the donor.
- Multimodal or vision evaluation.
- Production inference optimization.
- Publishing a model checkpoint to Hugging Face.
- Treating a heatmap, routing count, or REAP score as causal proof.

The likely future recipient is a small model around four billion parameters, but recipient selection and transfer design require a separate PRD.

## 5. Terminology

| Term | Definition |
|---|---|
| Expert | One routed MoE feed-forward module at a specific donor layer. This is not an autonomous agent. |
| Layer-expert pair | Stable identity `(layer_index, expert_index)`; expert indices are meaningful only within their layer and exact checkpoint. |
| REAP saliency | Mean router-weighted expert-output magnitude over tokens routed to the expert. |
| Candidate | An expert with strong domain-differential observational evidence; not yet proven critical. |
| Coding-critical | A candidate that passes the predefined causal, specificity, and reproducibility gates. |
| Extraction | Copying source tensors and metadata without altering their values. |
| Thinking condition | A separately recorded inference condition; thinking-enabled and thinking-disabled runs must never be silently pooled. |
| Prompt tokens | Tokens originating in the frozen input prompt. |
| Completion tokens | Tokens generated by the donor under the pinned decoding configuration. |

For expert `j` in a layer, the base REAP statistic is:

```text
S_j = (1 / N_j) * sum_t [g_j(t) * ||f_j(t)||_2]
```

where `g_j(t)` is the router weight, `f_j(t)` is the expert output, and the sum includes only tokens routed to that expert. Implementations must preserve the upstream REAP definition and record any normalization separately.

## 6. Donor contract

The only v0 donor is:

```text
Qwen/Qwen3.5-35B-A3B
```

At run initialization, resolve and pin an immutable Hugging Face revision. Save the downloaded `config.json`, tokenizer configuration, generation configuration, weight index, and file hashes in the run bundle.

Expected architecture, which must be verified from the pinned config rather than assumed:

- Model type: `qwen3_5_moe`
- 40 language-model layers
- Hidden size 2,048
- 256 routed experts per MoE layer
- Top-8 routed experts per token
- Expert intermediate size 512
- One shared expert path

If any expected field differs, stop before calibration and write a compatibility report. Never silently substitute Qwen3-Coder, Qwen3, Qwen3.5-4B, an unofficial quantization, or another revision.

The primary scientific run uses the official BF16 checkpoint. A quantized checkpoint may be evaluated later as a separate robustness condition but cannot replace the primary run without human approval.

## 7. Research hypotheses

### H-001 — Observational specialization

A subset of layer-expert pairs has higher coding-versus-control differential REAP saliency than expected under bootstrap resampling and label permutation.

### H-002 — Causal necessity

Ablating the selected set causes a larger coding-performance reduction than ablating size- and layer-matched random sets.

### H-003 — Domain specificity

The selected-set coding degradation is greater than its degradation on matched control tasks.

### H-004 — Stability

The high-confidence set is reasonably stable across dataset bootstrap samples, prompt templates, and repeated deterministic runs.

Failure to support any hypothesis is a valid v0 result. The agent must report a null result rather than relax gates after seeing the data.

## 8. Dataset requirements

### 8.1 Target strata

The frozen coding suite must contain separately labelled items from at least four strata:

1. Function synthesis from specifications.
2. Bug diagnosis and repair.
3. Code understanding or output prediction.
4. Repository-style software-engineering tasks that can be scored automatically.

At least two programming languages must be represented, with Python as the primary language. Dataset licenses, exact revisions, split names, sample identifiers, and content hashes must be recorded.

### 8.2 Controls

Use two control families:

- **Matched technical controls:** non-code problems matched as closely as practical for prompt length, reasoning demand, formatting, and technical vocabulary.
- **General controls:** factual, prose, and general-reasoning tasks used to detect broad model damage.

Do not compare long coding prompts only against short casual questions. Record token-length distributions and reject a dataset freeze if target/control lengths are grossly mismatched.

### 8.3 Splits

Use disjoint immutable splits:

- `calibration`: computes observational statistics.
- `selection`: chooses the candidate set and thresholds.
- `validation`: performs causal tests after the candidate set is frozen.
- `replication`: untouched until final confirmation.

No validation or replication labels may influence candidate ranking. Decontaminate exact duplicates and near-duplicates across splits.

### 8.4 Initial scale

The roadmap uses successively larger pilots. The full v0 target is at least 500 scored coding items and 500 controls, subject to the approved compute budget. If cost prevents this minimum, stop with an explicitly incomplete result.

## 9. Experimental conditions

Run and report these conditions separately:

| ID | Condition | Purpose |
|---|---|---|
| C0 | Baseline, thinking disabled, deterministic decoding | Primary low-variance attribution condition |
| C1 | Baseline, thinking enabled, deterministic or seeded decoding | Determine whether reasoning changes routing |
| C2 | Selected-set ablation under C0 | Necessity test |
| C3 | Layer-matched random-set ablation under C0 | Null distribution |
| C4 | Frequency-matched random-set ablation under C0 | Controls for popular experts |
| C5 | Lowest-differential set ablation under C0 | Negative control |
| C6 | Selected-set ablation under C1 | Reasoning robustness |

Prompt tokens and completion tokens must be summarized both separately and jointly. The primary candidate ranking uses prompt plus teacher-forced reference/accepted completion tokens if the runtime supports it reproducibly. Free-generation statistics are a secondary analysis because different generations create different token trajectories.

## 10. Functional requirements

### FR-001 — Environment preflight

The system shall record GPU model/count, driver, CUDA, PyTorch, Transformers, REAP commit, Python packages, free disk, available memory, hostname, and Git revision before loading weights.

### FR-002 — Architecture adapter

The system shall identify Qwen3.5 MoE layers, routed experts, shared experts, router outputs, expert outputs, fused tensor layout, and quantization metadata. It shall include a tiny synthetic or real-token probe proving the mapping.

### FR-003 — Baseline evaluation

The system shall score the unmodified donor before collecting or interpreting attribution results. A task whose scorer cannot be reproduced shall be excluded with a recorded reason.

### FR-004 — Routing capture

For every analysed token and MoE layer, capture exactly `top_k` routed expert records containing expert index, rank, router weight, token reference, prompt/completion segment, and sample identifier.

### FR-005 — Activation capture

Capture the L2 norm needed for upstream-compatible REAP saliency without retaining full activations after aggregation unless a debug flag is explicitly enabled. Streaming aggregation is required to limit disk and memory use.

### FR-006 — Telemetry validation

Validate row counts against `analysed_tokens × moe_layers × top_k`, expert bounds, rank uniqueness, finite values, non-negative weights, monotonic routing ranks where applicable, and manifest hashes.

### FR-007 — Differential analysis

For every layer-expert pair, report target and control values for:

- Token routing count and routing rate.
- Mean and summed router weight.
- Mean expert-output norm.
- Standard REAP saliency.
- Domain-differential standardized effect.
- Bootstrap confidence interval.
- Label-permutation p-value or empirical null rank.

No unobserved expert may receive an invented zero saliency without a separate `observed=false` flag.

### FR-008 — Candidate freeze

Create a signed or hashed candidate manifest before validation. The manifest shall specify selection method, thresholds, number selected globally and per layer, and all source artifact hashes. Validation must not mutate this manifest.

### FR-009 — Expert intervention

Support masking an individual routed expert and a frozen set. Define masking semantics exactly: whether the route weight becomes zero, whether surviving weights are renormalized, and how insufficient routes are handled. Primary v0 uses zero contribution without router renormalization; alternative semantics are separate experiments.

### FR-010 — Causal controls

Generate at least 20 deterministic layer-matched random expert sets of equal cardinality. Random seeds and generated manifests must be saved before scoring.

### FR-011 — Causal scoring

Report absolute and relative score deltas for coding and controls, confidence intervals over items, random-set percentile, parse/error rates, latency, and perplexity or token loss where feasible.

### FR-012 — Extraction

For every validated pair, extract all tensors required to execute that routed expert, expected to include gate, up, and down projections plus associated scale tensors when quantized. Do not include the shared expert unless separately validated and labelled.

### FR-013 — Extraction verification

Reload the source and extracted artifacts independently and verify shape, dtype, tensor name, byte count, and cryptographic hash. For floating tensors, byte equality—not approximate equality—is required.

### FR-014 — Run bundle

Produce a self-contained manifest linking configurations, datasets, telemetry summaries, candidate sets, interventions, evaluation results, extracted tensors, logs, and hashes. Large model files may be referenced by immutable revision and hash rather than duplicated.

### FR-015 — Resumption

Every expensive stage shall write an atomic completion marker only after validation. Restarting the agent shall skip validated stages and rerun incomplete or corrupt stages.

## 11. Evidence gates

### Gate A — Instrumentation validity

Pass only if:

- Required router and activation signals are captured on the pinned model.
- Telemetry invariants pass on a minimum 10-sample pilot.
- Capture-on versus capture-off baseline outputs and scores are identical under deterministic decoding.
- Peak memory leaves a documented safety margin or the batch/context is reduced.

### Gate B — Baseline validity

Pass only if at least 95% of frozen evaluation items are scoreable and repeated deterministic runs agree exactly, excluding documented nondeterministic kernels.

### Gate C — Candidate evidence

Pass only if the selected set beats the label-permuted null and has median bootstrap Jaccard stability of at least 0.60. This threshold is a prototype decision rule, not a universal scientific constant.

### Gate D — Causal criticality

Call the set `coding-critical-v0` only when all are true:

- Selected-set coding degradation is at least twice the median degradation of layer-matched random sets.
- It is at or above the 95th percentile of the random-set degradation distribution.
- Coding degradation exceeds general-control degradation by at least 2 absolute percentage points or a pre-registered equivalent standardized effect.
- The direction of the result repeats on the untouched replication split.
- Output validity does not collapse broadly enough to make the domain comparison meaningless.

If Gate D fails, extracted artifacts must be labelled `observational-candidates`, not `coding-critical`.

### Gate E — Extraction integrity

Pass only if every extracted tensor is byte-identical to its pinned source and the manifest accounts for every expected tensor.

## 13. Non-functional requirements

- **Reproducibility:** pin model, datasets, dependencies, code, seeds, prompts, and decoding settings.
- **Auditability:** never overwrite a completed run; all derived artifacts reference source hashes.
- **Budget safety:** estimate each stage before execution and stop before exceeding the configured GPU-hour or monetary cap.
- **Failure isolation:** one failed sample is quarantined; systematic failures stop the stage.
- **Storage discipline:** aggregate activations online; do not save sensitive prompts or full activations unnecessarily.
- **Determinism:** use greedy decoding for the primary condition and deterministic kernels where supported; record exceptions.
- **Scientific honesty:** distinguish observed routing, heuristic saliency, causal necessity, and transferability.
- **Security:** never commit tokens, credentials, private datasets, model weights, or provider secrets.

## 14. Risks and mitigations

| Risk | Consequence | Mitigation |
|---|---|---|
| Qwen3.5 unsupported by upstream REAP | Incorrect hooks or no telemetry | Build and validate a model adapter before full calibration |
| Fused MoE kernels hide expert outputs | REAP statistic unavailable | Use an instrumentable Transformers path for calibration; use serving runtimes only for separate throughput tests |
| Coding/control mismatch | False specialization | Length- and difficulty-aware controls; report distributions |
| Thinking changes token trajectories | Confounded rankings | Separate C0/C1 runs and manifests |
| Popular general experts dominate | False coding attribution | Differential scoring and frequency-matched controls |
| Ablation breaks routing mechanics | Invalid causal result | Pre-register exact masking semantics and test one expert first |
| Quantization changes ranking | Non-transferable evidence | BF16 primary; quantization as a labelled robustness experiment |
| Extracted set is too large | Impractical future transfer | Report Pareto curves by cardinality; do not change causal thresholds post hoc |
| Autonomous agent loops or overspends | Wasted GPU budget | Stage caps, retry limits, heartbeat logs, and fail-closed gates |

## 15. v0 success definition

v0 is complete when one of these honest terminal outcomes is reached:

1. **Positive result:** Gates A–E pass and a verified `coding-critical-v0` expert bundle is produced.
2. **Null result:** instrumentation and evaluation are valid, but Gate C or D fails; evidence and observational candidates are published without a criticality claim.
3. **Feasibility failure:** the exact donor cannot be instrumented within hardware or software constraints; a reproducible failure report identifies the blocking component.

Only outcome 1 authorizes proposing the separate small-host bridge experiment. None of the outcomes automatically authorize GLM execution; GLM requires a human go decision after reviewing the v0 report.
